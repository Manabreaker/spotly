# Spotly event creation implementation plan

> **For agentic workers:** Use superpowers:executing-plans to implement task-by-task.

**Goal:** Deliver the approved event form, persistent cross-device drafts and research telemetry, push to GitHub and deploy it with PostgreSQL.
**Architecture:** One FastAPI/Jinja application; browser controller saves versioned JSON drafts and batched events; PostgreSQL serializes mutations per invitation. Immutable originals and derived WebP images live in a persistent data directory.
**Tech Stack:** Python 3.14, FastAPI/Pydantic 2, SQLAlchemy 2/psycopg 3, PostgreSQL 18, Alembic, Pillow/pillow-heif, HTML/CSS/JS, Docker Compose/Caddy.
**Spec:** ../specs/2026-10-15-spotly.md

## Global constraints

- Preserve the two existing diagrams and all unrelated files.
- Never stage ignored paths; data, credentials and scratch remain outside Git.
- Any UUID initializes a form without a pre-issued invitation; one event per UUID.
- A restart preserves the previous attempt, values, photos and telemetry.
- Up to five photos; 30,000,000 bytes and 100,000,000 pixels each; HEIC supported, RAW excluded.
- Drafts accept invalid inputs; completion validates future timezone-aware date, duration 1..43200 minutes, price 1..999999999 kopecks, capacity 1..1000000.
- Text limits: title 150, description 10000, address 500, URL 4096, feedback 2000.
- Browser-created verification records are intentionally retained in the production DB.
- User authorizes implementation, Git push and deployment; use postgres DB user with a generated password, never exposed publicly.

## Review focus

- Stale tabs must not overwrite a restarted attempt or a completed event.
- Duplicate submit/photo/event requests must not create duplicates.
- Arbitrary text/URLs cannot create script execution or access other invitations.
- Interrupted uploads must not lose other draft fields or make false saved claims.
- DST/timezone changes and comma decimal normalization must preserve intent.

## Execution decisions

The user explicitly requested complete implementation, push, deployment and browser verification after approving the written spec. Execute natively without another approval handoff; no destructive replacement of existing services is authorized.
Server observation: Ubuntu 26.04, 1 vCPU, approximately 2 GB RAM/25 GB free, empty application ports. Add 4 GB swap and process images one at a time; prove limits on this host. The 2 vCPU/4 GB/40 GB values in the spec are an orientation, not a reason to silently reduce accepted photo limits.
